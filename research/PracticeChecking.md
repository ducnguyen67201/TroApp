# Practice checking product observations

Recorded October 9, 2026. These observations explain the product request; they are
not a specification of runtime behavior. [Architecture](../docs/Architecture.md)
owns the implemented system, and [README](../README.md) owns usage and validation.

Students should be able to request formative feedback without speaking or typing
“check for me.” A visible action and keyboard shortcut make the request discoverable.
Previewing captured work gives the student control over what is sent. Checking and
hand-in serve different purposes and should remain separate actions.

Feedback should follow teacher-approved exercise requirements and class materials.
Static screenshots, source code, and project structure provide different evidence;
none alone establishes every aspect of runtime behavior. Unverifiable requirements
need an explicit insufficient-evidence result and a path to teacher review.

Ideas discussed for future exploration include sandboxed code execution, PDF OCR
and visual extraction, richer Scratch control-flow analysis, and combining several
verification methods for one criterion. These are research directions rather than
committed capabilities. Judge quality should be calibrated using independently
teacher-reviewed examples across supported evidence types, with particular
attention to false passes and appropriate abstention.
